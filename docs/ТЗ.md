# Техническое задание: «Контур контроля лизинговой сделки» (прототип → продукт Sber2B)

Документ собирается по модулям. Здесь — модуль раннего предупреждения (страница «Мониторинг»). Разделы по остальным
модулям (вход и роли, жизненный цикл сделки, калькулятор класса, распознавание PDF, коннекторы) добавляются отдельно.
Описание API — `docs/openapi.yaml`.

## Раннее предупреждение о просрочке (страница «Мониторинг»)

### Назначение

Балльная карта по каждому клиенту лизинговой компании на конец месяца считает балл и зону (зелёная / жёлтая / красная):
насколько вероятен выход клиента в просрочку 60+ дней или расторжение договора в ближайшие 12 месяцев — и показывает
факторы, снижающие балл. Сигнал нужен раньше, чем просрочка 30+, после которой клиента передают в работу с проблемными
активами.

Текущая карта обучена на условных (сгенерированных) данных. Веса и точность показывают работу метода, а не реальные
зависимости. Везде, где показываются метрики, рядом должна быть эта оговорка.

### Данные: шаблон выгрузки

Шесть листов xlsx (шаблон — `GET /api/ews/template`, пример на демо-данных — `?example=1`). Клиент в выгрузке —
обезличенный «ID клиента» (служебный идентификатор учётной системы; прежний заголовок «Код клиента» тоже принимается).
Наименование и ИНН необязательны и в расчёт и в данные для обучения не идут.

| Лист | Поля | Источник |
|---|---|---|
| Клиенты | ID клиента, наименование и ИНН (необязательно), отрасль (по основному ОКВЭД), регион, дата начала отношений | учётная система лизинга |
| Договоры | номер, ID клиента, дата, тип предмета, стоимость предмета, аванс, срок, поручительство | учётная система лизинга |
| График | номер договора, дата платежа, сумма (действующая версия графика) | учётная система лизинга |
| Платежи | номер договора, дата поступления, сумма без пеней | учётная система лизинга |
| События | ID клиента, дата события, тип, сумма | учётная система, протоколы КПА, внешние источники по ИНН |
| Отчётность | ID клиента, год, дата представления, выручка (2110), чистая прибыль (2400), капитал (1300), активы (1600), долг (1410 + 1510) | ГИР БО, СПАРК, Контур по ИНН |

Типы событий: налоговая недоимка, иск к клиенту, исполнительное производство, смена руководителя, намерение кредитора
о банкротстве, реструктуризация, расторжение договора, изъятие предмета лизинга.

### Правила расчёта (`seed/ews/features.js`, требуют подтверждения заказчика)

- Оплата разносится на самый ранний неоплаченный платёж графика.
- Просрочка клиента — максимальная по его действующим договорам на конец месяца.
- Дефолт — просрочка 60+ дней на конец месяца или расторжение договора; исход — дефолт в следующие 12 месяцев.
- 19 признаков-кандидатов: платёжная дисциплина, сделка и предмет, внешние события за 12 месяцев, отчётность (с учётом
  даты представления), отрасль.
- Стоп-фактор «Намерение кредитора о банкротстве» переводит клиента в красную зону независимо от балла.
- Клиенты с просрочкой 30+ и после дефолта моделью не оцениваются (серая зона, работа с проблемными активами).
- Покрытие — отношение остатка лизинговых платежей к текущей стоимости предмета с учётом износа (нормы износа и пороги
  0,8 / 1,0 условные, задаёт заказчик).

Один и тот же модуль `features.js` применяется при обучении (Node.js), в API портала и в странице-прототипе — расхождение
баллов с Python проверяется скриптом `check_parity.js` (требование — 0,0000 балла).

### Метод обучения (`seed/ews/train.py`)

Интервалы с монотонностью и WoE (optbinning), отбор по IV ≥ 0,02, исключение дублей (|r| > 0,7) и признаков с обратным
знаком веса, логистическая регрессия со штрафом (C = 0,5), допустимое число факторов — по критериям Riley и соавт. (2019),
R²N = 0,3, наблюдение — клиент. Шкала: PDO 20, 600 баллов = шансы 50 : 1. Зоны: красная — 10 % худших баллов обучающей
выборки, жёлтая — следующие 20 %. Проверка — на отложенном периоде после даты разделения: Gini с 95 % интервалом против
правила «опоздание > 5 дней за 6 мес.», доли дефолтов по зонам, заблаговременность сигнала. Параметры метода и пороги
зон не меняются и не подбираются по периоду проверки без решения заказчика.

Эталон (27.10.2026, условный пул 2 500 клиентов): 13 признаков, зоны 574 / 612, Gini на проверке 0,64 (0,59–0,69),
правило — 0,37; 170 клиентов с дефолтом в обучении, допустимо 19 факторов.

### Работа в портале

Расчёт — на сервере (`app/monitoring/ews.js`): `features.js` + карта `model.json`, Python в рантайме не используется.

| Метод | Назначение | Роли |
|---|---|---|
| `GET /api/ews/model` | Действующая карта: версия, источник данных, признаки с интервалами и баллами, зоны, метрики проверки, оговорка | все |
| `GET /api/ews/portfolio?date=` | Клиенты на дату: балл, зона, изменение за месяц, остаток, просрочка, покрытие, 3 причины; сводка по зонам; переходы; число клиентов по зонам за 24 месяца | все |
| `GET /api/ews/clients/{code}?months=` | Карточка: история балла и просрочки, вклад каждого фактора (баллы из возможных), внешние события за 12 месяцев, договоры | все |
| `POST /api/ews/upload` | Проверка выгрузки по шаблону и расчёт по текущей карте | admin, team, talk |
| `GET /api/ews/template` | Пустой шаблон или пример (xlsx) | все |

Требования:
- Пользователь видит клиента по наименованию и ИНН; ID клиента — служебная связь «за кадром» (адрес карточки, подсказка).
  Источник реквизитов: справочник клиентов портала (`clients.client_code` = ID клиента), иначе столбцы «Наименование»
  и «ИНН» загруженной выгрузки. У условного портфеля — условные наименования «ООО «Пример-…»» и ИНН вида 000001NNNN
  с пометкой «условные реквизиты». Поиск и фильтры — по наименованию или ИНН.
- Демо-портфель по умолчанию — 420 клиентов, дата оценки 30.09.2026, метка «Демонстрационные данные» на странице.
- Загрузка: проверяются листы и обязательные столбцы, связи между листами (договоры без клиента, платежи без договора,
  договоры без графика), нераспознанные типы событий; при ошибке шаблона расчёт не выполняется. Файл не пишется на диск
  и не попадает в журнал; разобранные данные хранятся в памяти сервера 30 минут и видны только загрузившему.
- На странице — ключевая ставка Банка России с датой (коннектор ЦБ).
- Портал не отправляет данные выгрузки во внешние сервисы, в том числе в языковые модели.

### Процедура переобучения на выгрузке заказчика

Применяется к любому заказчику, передавшему данные по шаблону. Данные заказчика — вне репозитория, в каталоге с правами
700; код копируется туда же, чтобы обучение не затронуло эталонную карту в репозитории. На сервере — разовым
контейнером (`docker compose run --rm ews-train …`, профиль `train`), не в постоянно работающем контейнере портала.

```
cp seed/ews/{features.js,build_features.js,check_parity.js,train.py,xlsx_to_json.py} /data/customer/ews/
cd /data/customer/ews
python xlsx_to_json.py ../выгрузка.xlsx ../data.json [--date ГГГГ-ММ-ДД]
node build_features.js ../data.json ../snapshots.json
python train.py <дата_разделения> ../snapshots.json
node check_parity.js ../data.json
```

Правила:
1. Отчёт конвертера показывается целиком; при ошибках шаблона расчёт не продолжается.
2. До обучения — сверка восстановленной просрочки (`clientDpd` в `features.js`) с отчётом о просрочке учётной системы
   заказчика на 3–5 датах; правило разнесения оплат подтверждает заказчик.
3. Дата разделения: последние 12–18 месяцев срезов с полным горизонтом (12 месяцев после среза) — на проверку;
   выбирается вместе с заказчиком.
4. Схема по числу клиентов с дефолтом в обучении: от 60 — обычное обучение; 20–60 — малый лимит факторов, сообщить
   заказчику; менее 20 — не обучать автоматически, нужна экспертная карта.
5. После обучения показываются состав карты и причины исключений, знаки весов, Gini с интервалом против простого правила,
   зоны, заблаговременность.
6. Новая карта — отдельный файл `seed/ews/data/model_<заказчик>_<дата>.json`; переключение явное — переменная окружения
   `EWS_MODEL=model_<заказчик>_<дата>.json` и перезапуск сервиса; прежняя карта не удаляется. Карта, обученная на данных
   заказчика, не коммитится без решения заказчика: интервалы и пороги отражают его портфель.

Проверка процедуры на демо-данных (28.10.2026, выгрузка `xlsx_to_json.py data/demo.json demo.xlsx --reverse` как
«выгрузка заказчика», дата разделения 2024-03-31): конвертер — 420 клиентов, 607 договоров, 24 660 строк графика,
19 187 платежей, 1 792 события, 2 224 отчёта, связи без ошибок; срезов 15 506, клиентов с событием 61; `train.py` —
5 признаков (как в карте 14.10, интервалы и веса совпали), 33 клиента с дефолтом, допустимо 5; `check_parity.js` —
4 048 срезов, расхождение 0,0000. Конвертер туда и обратно (`--reverse`, затем обратно) и пример, выгруженный порталом,
дают срезы, идентичные исходным.

### Ограничения и вопросы к заказчику

- Пороги зон (10 % / 30 % худших), пороги покрытия (0,8 / 1,0) и нормы износа техники — условные, подтверждает заказчик.
- «Изменение среднего опоздания» и «Остаток платежей к стоимости предмета» сильны по отдельности, но при совместной оценке
  на условных данных получают обратный знак — на реальных данных проверить заново.
